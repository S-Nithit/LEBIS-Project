## วิดีโอ Data — 8:00–15:00 การค้นหาและการนับ

**รับต่อจากคิม** — คิมจบช่วงด้วยประโยค *"ต่อไปนีโอจะเล่าว่าเราค้นหาของที่ครบกำหนดยังไง ซึ่ง hash table ทำไม่ได้"*
ช่วงนี้จึงเริ่มจากสิ่งที่ hash table ทำไม่ได้ทันที ไม่ต้องแนะนำตัวยาว

**8:00–8:40 hash table ตอบได้ไม่ทุกคำถาม** · *บนจอ: ตารางในบทนำของรายงาน*
- "ผมนีโอครับ รับส่วนค้นหากับการนับ"
- "hash table ของคิมเร็วมาก แต่ตอบได้คำถามเดียว คือ รหัสนี้อยู่ไหน"
- "ร้านถามมากกว่านั้น สามแบบที่ hash table ตอบไม่ได้
  ลูกค้าจำรหัสไม่ได้ บอกแต่ชื่อ · เจ้าของร้านอยากรู้ว่ามีอะไรครบกำหนดก่อนวันนี้บ้าง · และว่างกี่ชิ้น เลยกำหนดกี่ใบ"
- "ข้อสองคือเหตุผลที่โปรเจกต์ยังต้องมี binary search ทั้งที่มี hash table แล้ว"

**8:40–10:10 binary search ทำงานยังไง** · *บนจอ: Flowchart 4 สลับกับโค้ด `binary_search` ใน search.py*
- ไล่ตามลูกศรใน Flowchart 4: "ดูตัวกลางก่อน ถ้าตรงคือจบ ถ้าตัวที่หาน้อยกว่าตรงกลาง แปลว่าต้องอยู่ครึ่งซ้าย ทิ้งครึ่งขวาทั้งก้อน"
- "**ทุกรอบที่เทียบ จำนวนที่เหลือลดลงครึ่งหนึ่ง** ข้อมูล 1,000 ชิ้นจึงเทียบแค่ประมาณ 10 ครั้ง เพราะสองยกกำลังสิบได้ 1,024
  ถ้าไล่ทีละตัว เฉลี่ยต้องเทียบ 500 ครั้ง"
- ชี้กล่อง `sort_by_code` ใน flowchart: "เงื่อนไขที่ห้ามลืมคือ list ต้องเรียงมาก่อน
  ถ้าไม่เรียง การตัดครึ่งจะตัดผิดข้าง แล้วคืน None ทั้งที่ของอยู่ในนั้น **และไม่มี error ฟ้องเลย**"
- ชี้บรรทัด `middle = low + (high - low) // 2`: "เขียนแบบนี้แทน low บวก high หารสอง เป็นท่ามาตรฐานกันตัวเลขล้นในภาษาที่ int มีขนาดจำกัด"
- "เขียนเป็นลูป ไม่ได้เรียกตัวเอง เพราะลูปไม่กินพื้นที่ stack เพิ่ม หน่วยความจำจึงเป็น O(1) ไม่ใช่ O(log n)"

**10:10–11:00 ค้นด้วยชื่อต้องคืนทุกตัว** · *บนจอ: notebook ส่วนที่ 3 ผลชุด B*
- "ค้นด้วยชื่อใช้ hash table ไม่ได้ เพราะแฮชต้องการ key ที่ตรงเป๊ะ กล้อง กับ กล้องรุ่นที่ 5 คำนวณได้คนละถัง"
- "และต้องคืน**ทุกตัว**ที่ตรง ไม่ใช่ตัวแรก เพราะชื่อซ้ำกันได้จริง ชุด B สร้างมาพิสูจน์ข้อนี้"
- ชี้ผล: "ค้นคำว่า เลนส์ รุ่นที่ 1 ได้ **4 รายการ** ชื่อตรงเป๊ะจริง 2 อีก 2 คือรุ่นที่ 11 กับ 12 ที่มีคำนี้อยู่ข้างใน
  ถ้าคืนแค่ตัวแรก ร้านจะปล่อยเช่าผิดชิ้น แล้วอีกชิ้นหายไปจากระบบเงียบๆ"

**11:00–12:15 ผลวัดจริง** · *บนจอ: ตาราง S1 ในรายงาน หรือตารางที่ 1 ใน `LEBIS_Final.ipynb` ส่วนที่ 3*
- "ชุดเล็ก 10 รายการ ไล่ทีละตัวเร็วกว่า binary search ด้วยซ้ำ **0.004 กับ 0.006 มิลลิวินาที**
  เพราะข้อมูลน้อยเกินกว่าที่การตัดครึ่งจะคุ้มค่าคำนวณตำแหน่ง
  O(log n) ไม่ได้แปลว่าเร็วกว่าเสมอ **แปลว่าโตช้ากว่า**"
- "ชุด D 1,000 รายการ binary search เร็วกว่าไล่ทีละตัว **12.4 เท่า** — 21.812 กับ 1.759 มิลลิวินาที"
- **ข้อนี้คือจุดที่อยากให้อาจารย์เห็นที่สุด:** "ข้อมูลโต 100 เท่าจากชุด A ไป D
  ทฤษฎีบอกว่า binary search ควรโต 300 เท่า เราวัดได้ **293** · hash table ควรโต 100 เท่า เราวัดได้ **99**
  ตัวเลขที่วัดจริงตรงกับที่ Big-O ทำนายไว้"
- "ส่วนไล่ทีละตัว ทฤษฎีบอก 10,000 เท่า แต่วัดได้ประมาณ 5,453
  ไม่ใช่เพราะทฤษฎีผิด แต่เพราะที่ 10 รายการ เวลาส่วนใหญ่หมดไปกับค่าใช้จ่ายคงที่ ตัวหารเลยใหญ่เกินจริง"

**12:15–13:30 คำถามแบบช่วง — สิ่งที่ hash table ทำไม่ได้** · *บนจอ: โค้ด `find_due_before` + ผลชุด D*
- "กลับมาที่คำถามของคิม มีอะไรครบกำหนดคืนก่อนวันที่ 1 ตุลาคมบ้าง"
- "hash table รู้แค่ว่ารหัสที่ตรงเป๊ะอยู่ถังไหน ไม่มีความคิดเรื่องก่อนหรือหลัง คำถามแบบนี้จึงต้องไล่ทั้งตาราง"
- "ถ้า list เรียงตามวันคืนมาแล้ว binary search หาขอบของช่วงได้ใน O(log n) แล้วตัดเอาทั้งก้อน
  รวมเป็น **O(log n + k)** k คือจำนวนคำตอบ ซึ่งยังไงก็ต้องคัดลอกออกมาอยู่แล้ว"
- ชี้ผล: "ชุด D หาได้ **275 ใบ** ตรงกับการไล่ทีละตัวทุกใบ"
- "สังเกตว่า high เริ่มที่ len ไม่ใช่ len ลบหนึ่ง เพราะคำตอบอาจเป็นทั้ง list คือทุกใบเลยกำหนดหมด"

**13:30–14:30 การนับ** · *บนจอ: Flowchart 5 + ตาราง S2*
- "นับว่าว่างกี่ชิ้น แยกสถานะ และเลยกำหนดกี่ใบ สามฟังก์ชันโครงเดียวกัน เดินข้อมูลรอบเดียว"
- "ทั้งสามเป็น O(n) และ**ไม่มีทางลัด** การนับไม่มีตัวที่ใช่ให้หยุด ต้องดูครบทุกชิ้นถึงจะได้ตัวเลข
  binary search ช่วยไม่ได้เพราะไม่มีเป้าหมายให้เทียบ hash table ก็ช่วยไม่ได้เพราะตอบได้แค่ตัวนี้อยู่ไหน"
- ชี้จุดที่ต่างกันใน Flowchart 5:
  - "นับของว่างต้องข้ามของชำรุด ถึงจะวางอยู่บนชั้นก็ปล่อยเช่าไม่ได้ และบวกเป็นจำนวนชิ้น ไม่ใช่บวกหนึ่ง"
  - "นับแยกสถานะคืนครบสามคีย์เสมอแม้ค่าเป็นศูนย์"
  - "นับที่เลยกำหนดต้องเช็ค None ก่อน ของที่คืนแล้วไม่มีวันกำหนด ถ้าไม่เช็ค Python จะ error ทันที"
- ชี้ตาราง S2: "ชุด D ว่างบนชั้น **1,309 ชิ้น** · เลยกำหนด **275 ใบ** ตรงกับที่ binary search หาได้เมื่อกี้"

**14:30–15:00 ใช้ในเว็บจริง + ส่งต่อกุล** · *บนจอ: หน้า Workspace ของเว็บ*

## อาจารย์น่าจะถามอะไร (เตรียมคำตอบไว้)

| คำถาม | คำตอบสั้น |
|---|---|
| ทำไมไม่ใช้ `bisect` ของ Python | โจทย์ให้เขียนเอง และการเขียนเองทำให้อธิบายได้ทุกบรรทัด notebook ของนีโอวัดเทียบกับ `bisect` ไว้ด้วย เวลาระดับเดียวกัน `bisect` เร็วกว่าเล็กน้อยเพราะเขียนด้วยภาษา C ไม่ใช่เพราะอัลกอริทึมดีกว่า |
| hash table เร็วกว่าแล้วจะเขียน binary search ทำไม | ตอบคนละคำถาม hash table ตอบได้แค่ "รหัสนี้อยู่ไหน" binary search บน list ที่เรียงแล้วตอบ "มีอะไรบ้างก่อนวันนี้" ได้ ซึ่งเป็นคำถามที่ร้านถามทุกเช้า |
| ทำไมการนับเป็น O(n) | ไม่มีตัวที่ใช่ให้หยุด ต้องดูครบทุกชิ้น ข้ามตัวไหนไปตัวเลขก็ผิดทันที |
| ทำไมชุดเล็กไล่ทีละตัวชนะ | ค่าคงที่ของการคำนวณตำแหน่งแพงกว่าการไล่ 10 ตัว Big-O พูดถึงตอน n โต |
| ทำไม linear โตไม่ถึง 10,000 เท่า | ที่ n = 10 เวลาส่วนใหญ่เป็นค่าใช้จ่ายคงที่ ไม่ใช่การเทียบจริง ตัวหารจึงใหญ่เกินจริง อัตราส่วนเลยดูเล็กลง |
| ชุดข้อมูลสุ่มหรือเปล่า | ไม่สุ่มสด ใช้ seed ตายตัวและตรึงวันอ้างอิงไว้ รันกี่ครั้งก็ได้ข้อมูลเดิม ตัวเลขในรายงานจึงซ้ำได้ |
| ทำไมใส่ของชำรุดทุกลำดับที่ 7 | ให้ชุดเล็กมีของชำรุดอย่างน้อยชุดละชิ้น ไม่งั้นเงื่อนไขข้ามของชำรุดจะไม่เคยถูกทดสอบเลย |
