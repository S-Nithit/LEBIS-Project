## 2.1 กระบวนการที่เลือก

หัวข้อที่แล้วแก้ปัญหา "ของรหัสนี้อยู่ไหน" ด้วยตารางแฮช ซึ่งตอบได้เร็วที่สุดเมื่อรู้รหัสที่ตรงเป๊ะ
แต่คำถามที่ร้านถามจริงไม่ได้มีแค่แบบนั้น

- ลูกค้าจำรหัสไม่ได้ บอกแต่ชื่อ *"ขอเลนส์ตัวที่เคยเช่าไป"* — ต้องค้นจากชื่อบางส่วน และชื่อซ้ำกันได้
- เจ้าของร้านเปิดหน้าตอนเช้า — ต้องรู้ว่า **ว่างกี่ชิ้น อยู่กับลูกค้ากี่ชิ้น เลยกำหนดคืนกี่ใบ**
- ก่อนปิดร้าน — ต้องรู้ว่า *"มีอะไรครบกำหนดคืนก่อนวันที่ X บ้าง"* ซึ่งเป็นคำถามแบบ **ช่วง** ไม่ใช่ค่าเดียว

สองข้อหลังตารางแฮชตอบไม่ได้เลย เพราะแฮชคำนวณตำแหน่งจาก key ที่ตรงเป๊ะเท่านั้น
ส่วนนี้จึงเลือกอัลกอริทึมกลุ่ม **Searching** และ **Counting** โดยเขียน binary search ขึ้นเองทั้งหมด
ไม่ได้ใช้ `bisect` ของ Python (ใช้เป็นตัวเทียบผลเท่านั้น)

## 2.2 โครงสร้างข้อมูลและเงื่อนไขก่อนค้น

ทั้งทีมใช้ record เดียวกัน 8 ฟิลด์ จาก `make_dataset()`

`code` · `name` · `category` · `total` · `available` · `borrower` · `due_date` · `status`

binary search ต้องการสิ่งเดียวที่ list ธรรมดาไม่มี คือ **ข้อมูลต้องเรียงมาก่อน**

> 🔴 ถ้า list ไม่เรียงตาม `code` การตัดครึ่งจะตัดผิดข้าง แล้ว **คืน `None` ทั้งที่ของอยู่ในนั้น**
> เป็นความผิดพลาดที่ไม่มี error ฟ้องเลย ต้องมีคนตาดีไปเห็นเอง
> จึงมี `sort_by_code()` เตรียมไว้ให้เรียกก่อนเสมอ และคืน list ใหม่ ไม่แก้ของเดิม

ในระบบจริง list ที่เรียงตาม `due_date` มาจาก **merge sort ของ Kul** โดยตรง (`sort_by_due_date()`)
งานสองคนนี้ต่อกัน จึงตกลงกันว่าทุกฟังก์ชันคืน list ใหม่เสมอ ไม่แก้ของที่คนอื่นถืออยู่

## 2.3 การค้นหาสามเส้นทาง

เลือกเส้นทางตาม **ชนิดของคำถาม** ไม่ใช่ตามว่าอันไหนเร็วที่สุด

| เส้นทาง | ฟังก์ชัน | ใช้เมื่อ | เวลา |
|---|---|---|---|
| linear | `linear_search` | ไม่ได้เรียง ไม่มีตารางแฮช ใช้เป็นตัวเทียบ | O(n) |
| hash | `hash_lookup` | รู้รหัสตรงเป๊ะ และมีตารางของ Kim | O(1) เฉลี่ย |
| **binary** | **`binary_search`** | **รหัสตรงเป๊ะบน list ที่เรียงแล้ว — ตัวที่เขียนเอง** | **O(log n)** |
| ชื่อบางส่วน | `search_by_name` | ลูกค้าจำได้แต่ชื่อ | O(n) |

**วิธีคิดของ binary search** — ดูตัวกลางก่อน ถ้าตรงคือจบ ถ้าตัวที่หาน้อยกว่าตรงกลางแปลว่าต้องอยู่ครึ่งซ้าย
ทิ้งครึ่งขวาทั้งก้อน และกลับกัน **ทุกรอบที่เทียบจบ จำนวนที่เหลือต้องดูลดลงครึ่งหนึ่ง**
ข้อมูล 1,000 ชิ้นจึงเทียบแค่ประมาณ 10 ครั้ง เพราะ 2¹⁰ = 1,024

เขียนเป็นลูป ไม่ใช่เรียกตัวเอง เพราะลูปไม่กินพื้นที่ stack เพิ่ม **หน่วยความจำจึงเป็น O(1) ไม่ใช่ O(log n)**
และใช้ `middle = low + (high - low) // 2` แทน `(low + high) // 2` ซึ่งเป็นท่ามาตรฐานกันค่าล้น
ในภาษาที่ `int` มีขนาดจำกัด (Python ไม่ล้น แต่เขียนให้ถูกหลักไว้)

**`search_by_name` ต้องคืนทุกตัวที่ตรง ไม่ใช่ตัวแรก** เพราะชื่อซ้ำกันได้จริงในร้าน
ถ้าคืนตัวแรกเหมือน `linear_search` ผู้ใช้จะได้ของผิดชิ้นโดยไม่รู้ตัว แปลว่าปล่อยเช่าผิดชิ้น
และของอีกชิ้นจะหายไปจากระบบเงียบๆ ชุด B สร้างมาเพื่อพิสูจน์ข้อนี้โดยเฉพาะ

## 2.4 คำถามแบบช่วง — จุดที่ตารางแฮชแทนไม่ได้

`find_due_before(sorted_by_due, limit_date)` ตอบคำถาม *"มีอะไรครบกำหนดคืนก่อนวันที่ X"*

ใช้การตัดครึ่งหาขอบซ้ายสุดที่ `due_date >= limit_date` ด้วย O(log n) แล้วตัดเอาทุกตัวก่อนหน้านั้นออกมาทั้งก้อน
รวมเป็น **O(log n + k)** โดย k คือจำนวนคำตอบ ซึ่งต้องเสียเวลาคัดลอกออกมาอยู่แล้วไม่ว่าใช้วิธีไหน

สังเกตว่า `high` เริ่มที่ `len()` ไม่ใช่ `len() - 1` เพราะคำตอบอาจเป็น "ท้ายสุด" คือไม่มีตัวไหนถึงเกณฑ์เลย

**ตารางแฮชทำแบบนี้ไม่ได้** แฮชรู้แค่ว่า key ที่ตรงเป๊ะอยู่ถังไหน ไม่มีความคิดเรื่อง "ก่อน/หลัง"
คำถามแบบช่วงจึงต้องไล่ดูทั้งตาราง กลายเป็น O(n) — **นี่คือเหตุผลที่โปรเจกต์ยังต้องมี binary search
ทั้งที่มีตารางแฮชของ Kim อยู่แล้ว**

## 2.5 การนับ

สามฟังก์ชัน โครงเหมือนกันทั้งหมด เดินผ่านข้อมูลรอบเดียว ต่างกันแค่เงื่อนไขและสิ่งที่บวก

| ฟังก์ชัน | นับอะไร | จุดที่พลาดง่าย |
|---|---|---|
| `count_available` | จำนวน **ชิ้น** ที่ว่างบนชั้น | ของชำรุดไม่นับ ถึงจะวางอยู่ก็ปล่อยเช่าไม่ได้ |
| `count_by_status` | จำนวน **รายการ** แยกสถานะ | คืนครบ 3 คีย์เสมอ แม้ค่าเป็น 0 |
| `count_overdue` | จำนวนใบที่เลยกำหนด | ของที่คืนแล้วไม่มี `due_date` ต้องข้ามก่อนเทียบ ไม่งั้น `TypeError` |

**ทั้งสามเป็น O(n) และไม่มีทางลัด** — การนับต่างจากการค้นตรงที่ไม่มี "ตัวที่ใช่" ให้หยุด
ต้องดูครบทุกชิ้นถึงจะสรุปตัวเลขได้ binary search ใช้แทนไม่ได้เพราะการตัดครึ่งต้องมีเป้าหมายเดียว
ที่เทียบได้ว่ามากกว่าหรือน้อยกว่า ส่วนตารางแฮชตอบได้แค่ "ตัวนี้อยู่ไหน" ไม่ใช่ "มีกี่ตัวที่เข้าเงื่อนไข"

`count_by_status` เดินรอบเดียวได้ครบทั้งสามตัวเลข ไม่ใช่วนสามรอบแยกกัน ผลเท่ากันแต่อ่านข้อมูลน้อยกว่าสามเท่า

**เทียบวันที่ด้วยการเทียบข้อความได้เลย** เพราะ `YYYY-MM-DD` เรียงจากหน่วยใหญ่ไปเล็ก
`"2026-09-26" < "2026-10-01"` เป็นจริงทั้งเชิงข้อความและเชิงวันที่ — ถ้าเก็บเป็น `DD/MM/YYYY` ข้อนี้จะไม่จริงทันที

## 2.6 ความซับซ้อน (Big-O)

| ฟังก์ชัน | เวลา | หน่วยความจำ | กรณีแย่สุดเกิดเมื่อ |
|---|---|---|---|
| `linear_search` | O(n) | O(1) | ไม่มีของชิ้นนั้นอยู่เลย ต้องดูครบถึงสรุปได้ |
| **`binary_search`** | **O(log n)** | **O(1)** | ของอยู่ที่ขอบสุด ใช้ครบ log₂(n) รอบ |
| `hash_lookup` | O(1) เฉลี่ย | O(n) ที่ตาราง | ทุกรหัสไปกองถังเดียวกัน กลายเป็น O(n) |
| `search_by_name` | O(n) | O(k) ที่ผลลัพธ์ | ทุกรายการมีคำนั้นอยู่ในชื่อ |
| `sort_by_code` | O(n log n) | O(n) | — |
| **`find_due_before`** | **O(log n + k)** | O(k) | ทุกรายการเข้าเงื่อนไข (k = n) |
| `count_available` · `count_by_status` · `count_overdue` | O(n) | O(1) | ทุกกรณีเท่ากัน ไม่มีทางลัด |

**ทำไม binary เป็น O(1) หน่วยความจำ ทั้งที่แบ่งครึ่งซ้ำ** — เพราะเขียนเป็นลูป ไม่ใช่ recursion
ตัวแปรที่ใช้มีแค่ `low` `high` `middle` สามตัว ไม่ว่าข้อมูลจะมีกี่รายการ
ถ้าเขียนแบบเรียกตัวเอง แต่ละชั้นจะกิน stack frame หน่วยความจำจะกลายเป็น O(log n)

## 2.8 ผลการวัด

แต่ละช่องรัน 3 รอบแล้วเฉลี่ยด้วย `time.perf_counter()` วิธีเดียวกับหัวข้อ 1 และ 3
เวลาเตรียมข้อมูลไม่ถูกนับรวม หน่วยเป็นมิลลิวินาที · "เร็วขึ้น" = เวลา linear ÷ เวลา binary

**ตาราง S1 — เวลาค้นครบทุก code หนึ่งรอบ**

| ชุด | จำนวน | linear | binary | hash | เร็วขึ้น |
|---|---:|---:|---:|---:|---:|
| A | 10 | 0.004 | 0.006 | 0.016 | 0.6× |
| B | 12 | 0.004 | 0.007 | 0.018 | 0.6× |
| C | 10 | 0.003 | 0.006 | 0.015 | 0.6× |
| D | 1,000 | 21.812 | 1.759 | 1.580 | **12.4×** |

**ตาราง S2 — ผลการนับ**

| ชุด | ว่างบนชั้น (ชิ้น) | ok | out | broken | เลยกำหนด |
|---|---:|---:|---:|---:|---:|
| A | 24 | 9 | 0 | 1 | 3 |
| B | 14 | 7 | 4 | 1 | 4 |
| C | 10 | 5 | 4 | 1 | 4 |
| D | 1,309 | 616 | 242 | 142 | 275 |

**ตาราง S3 — ค้นด้วยชื่อที่ซ้ำกัน (ชุด B)**

ค้นคำว่า `"เลนส์ รุ่นที่ 1"` ได้ **4 รายการ** — `LEN-0001` (0/2, out) · `LEN-0002` (3/5, ok) · `LEN-0011` (4/5, ok) · `LEN-0012` (0/5, out)

ในจำนวนนี้ชื่อตรงกันเป๊ะจริงๆ มี 2 รายการ ที่เกินมาคือชื่อที่มีคำนี้อยู่ข้างใน เช่น *"รุ่นที่ 11"* ก็มีคำว่า *"รุ่นที่ 1"* อยู่
**ค้นแบบนี้ถูกสำหรับช่องค้นหาในหน้าเว็บ** เพราะผู้ใช้พิมพ์ไม่ครบก็ยังเจอ

**ตาราง S4 — คำถามแบบช่วง (ชุด D)**

*"มีของอะไรบ้างที่ครบกำหนดคืนก่อน 2026-10-01"* — binary search ได้ **275 รายการ** · นับทีละตัวแบบ O(n) ได้ **275 รายการ** → **ตรงกัน**

### อ่านผล

1. **ชุดเล็ก (A–C) linear เร็วกว่า binary** (0.004 vs 0.006 ms) — ข้อมูลน้อยเกินกว่าที่การตัดครึ่ง
   จะคุ้มค่าใช้จ่ายของการคำนวณตำแหน่ง **O(log n) ไม่ได้แปลว่าเร็วกว่าเสมอ แปลว่าโตช้ากว่า**
   ถ้าวัดแค่ชุดเล็กแล้วสรุปว่า binary ไม่ดี คือสรุปผิด
2. **ชุด D binary เร็วกว่า linear 12.4 เท่า** (21.812 vs 1.759 ms) และ hash เร็วกว่า linear 13.8 เท่า (1.580 ms)
3. **อัตราการโตตรงกับทฤษฎีแทบเป๊ะ** — ข้อมูลโตขึ้น 100 เท่าจาก A ไป D และการวัดนี้ค้นครบทุก code
   คือค้น n ครั้ง จึงคาดได้ว่า
   - binary: n × O(log n) → ควรโต 100 × 3 = **300 เท่า** · วัดได้ 1.759 ÷ 0.006 = **293 เท่า**
   - hash: n × O(1) → ควรโต **100 เท่า** · วัดได้ 1.580 ÷ 0.016 = **99 เท่า**

   สองตัวนี้ตรงกับที่ Big-O ทำนายไว้ในระดับที่ไม่ใช่เรื่องบังเอิญ
4. **linear โตน้อยกว่าที่ทฤษฎีบอก** — n × O(n) ควรโต 10,000 เท่า แต่วัดได้ 21.812 ÷ 0.004 ≈ 5,453 เท่า
   ไม่ใช่เพราะทฤษฎีผิด แต่เพราะที่ n = 10 เวลาส่วนใหญ่หมดไปกับค่าใช้จ่ายคงที่ (เรียกฟังก์ชัน ตั้งลูป)
   ไม่ใช่การเปรียบเทียบจริง ตัวหารจึงใหญ่เกินจริง **ทำให้อัตราส่วนดูเล็กลง**
   ข้อนี้คือเหตุผลเดียวกับข้อ 1 มองจากอีกมุมหนึ่ง
5. **hash กับ binary ใกล้กันมากบนชุด D** (1.580 vs 1.759 ms) ทั้งที่ Big-O ต่างกันคนละชั้น
   เพราะ log₂(1,000) ≈ 10 ซึ่งยังเป็นเลขเล็ก ความต่างจะเห็นชัดเมื่อ n โตกว่านี้มาก
   **แต่ความเร็วไม่ใช่เหตุผลที่เลือก binary** — เหตุผลคือตาราง S4 ที่แฮชตอบไม่ได้
6. **การนับไม่มีตารางเทียบความเร็ว** เพราะไม่มีวิธีอื่นให้เทียบ ทุกวิธีต้องดูครบทุกชิ้นเหมือนกันหมด

## 2.11 โค้ดนี้ถูกใช้ในระบบจริง ไม่ใช่เขียนไว้ส่งอย่างเดียว

- `overdue_borrows` ← `count_overdue()`

เท่ากับเขียนนิยามของคำว่า "ว่าง" และ "เลยกำหนด" ไว้สองที่ **แล้ววันหนึ่งสองที่นั้นจะไม่ตรงกันโดยไม่มีใครรู้**
