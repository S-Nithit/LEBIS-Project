## 3.3 การเรียงลำดับ

### merge sort — แบ่งครึ่งแล้วผสาน

```
merge_sort(items, key):
    ถ้า len(items) ≤ 1:  คืน list(items)          ← ชิ้นเดียวถือว่าเรียงแล้วเสมอ (base case)
    middle = len(items) // 2
    left  = merge_sort(items[:middle], key)       ← เรียกตัวเองกับครึ่งซ้าย
    right = merge_sort(items[middle:], key)       ← เรียกตัวเองกับครึ่งขวา
    คืน _merge(left, right, key)
```

`_merge` ผสานสอง list ที่เรียงแล้วให้เป็นก้อนเดียวที่ยังเรียงอยู่ — ไล่เทียบตัวหน้าสุดของทั้งสองฝั่ง
หยิบตัวที่เล็กกว่าออกมาก่อน พอฝั่งใดหมด อีกฝั่งที่เหลือเรียงอยู่แล้ว จึงต่อท้ายได้ทันที

```
i = j = 0 · merged = []
ขณะที่ i < len(left) และ j < len(right):
    ถ้า key(left[i]) <= key(right[j]):   หยิบ left[i]   แล้ว i += 1
    ไม่อย่างนั้น:                        หยิบ right[j]  แล้ว j += 1
merged ต่อท้ายด้วย left[i:] และ right[j:]
```

เขียนแบบ recursion เพราะการแบ่งครึ่งซ้ำเข้ากับรูปแบบนี้ตามธรรมชาติ
ความลึกประมาณ log₂(n) ชั้น — 1,000 รายการลึกประมาณ 10 ชั้น ไม่เสี่ยง stack overflow

### stable sort — ทำไมเขียน `<=` ไม่ใช่ `<`

stable sort คือการเรียงที่ **ของที่ค่าเท่ากันยังอยู่ในลำดับเดิม**

ใน `_merge` ฝั่งซ้ายคือของที่อยู่ก่อนในข้อมูลเดิมเสมอ เมื่อค่าเท่ากัน `<=` ทำให้หยิบตัวจากฝั่งซ้ายก่อน
ลำดับเดิมจึงไม่ถูกสลับ ถ้าเขียน `<` ตัวจากฝั่งขวาจะถูกหยิบก่อน ของที่ค่าเท่ากันจะสลับที่กันโดยไม่มีเหตุผล
อักขระตัวเดียวนี้คือจุดเดียวที่ทำให้ merge sort ตัวนี้เป็น stable

ผลในระบบจริง: ใบยืมที่ครบกำหนดวันเดียวกันยังเรียงตามลำดับที่ฐานข้อมูลส่งมา (ตาม id)
ไม่สลับไปมาทุกครั้งที่เปิดหน้า `verify()` ในไฟล์ตรวจข้อนี้ไว้ด้วยข้อมูลที่ค่าเท่ากัน
และเทียบกับ `sorted()` ซึ่งเป็น stable

`bubble_sort` ก็เป็น stable เช่นกัน เพราะสลับเฉพาะเมื่อตัวหน้า **มากกว่า** ตัวหลัง (`>`) ค่าเท่ากันไม่สลับ

### bubble sort — ตัวเทียบ

```
result = list(items)                       ← ก็อป list ก่อน ไม่แก้ของเดิม
ทุกรอบ round_index = 0 … n−1:
    swapped = False
    ไล่ i = 0 … n − round_index − 2:
        ถ้า key(result[i]) > key(result[i+1]):  สลับ แล้ว swapped = True
    ถ้ารอบนี้ไม่มีการสลับเลย:  หยุดทันที      ← เรียงเสร็จแล้ว ไม่ต้องวนต่อ
```

แต่ละรอบ ของที่ค่ามากที่สุดที่เหลือจะลอยไปอยู่ท้ายสุด รอบถัดไปจึงไล่สั้นลงหนึ่งตัว
ตัวหยุดเมื่อไม่มีการสลับทำให้ข้อมูลที่เรียงมาแล้วจบในรอบเดียว

### ฟังก์ชันที่ระบบเรียกใช้

| ฟังก์ชัน | ทำอะไร |
|---|---|
| `sort_by_due_date(items)` | กรองใบที่ `due_date` เป็น `None` ออกก่อน แล้วเรียก `merge_sort` ด้วย `key = due_date` เรียงน้อยไปมาก ใบที่ค้างนานสุด (วันเก่าสุด) จึงอยู่บนสุด |
| `sort_by_available(items)` | `merge_sort` ตัวเดียวกัน เปลี่ยนแค่ `key = available` ของที่เหลือน้อยสุดอยู่บนสุด |

ทำไม `sort_by_due_date` ต้องกรอง `None` ออก: ของที่ไม่มีคนยืมไม่มีวันครบกำหนดให้เรียงตั้งแต่แรก
และ Python เทียบ `None` กับข้อความไม่ได้ (โยน `TypeError` ทันที)
ผลลัพธ์จึงมีแค่ใบที่มีวันครบกำหนด — ชุด D มี **685 จาก 1,000 รายการ**

`due_date` เก็บเป็นข้อความรูปแบบ `YYYY-MM-DD` ซึ่งเรียงแบบข้อความได้ลำดับเดียวกับวันที่จริง
(ปีมาก่อน แล้วเดือน แล้ววัน) จึงเทียบด้วย `<=` ได้ตรงๆ ไม่ต้องแปลงเป็นวันที่ก่อน

## 3.4 การจัดกลุ่ม

ทั้งสองฟังก์ชันเดินผ่านข้อมูล **รอบเดียว** แล้วหย่อนแต่ละรายการลงถังตามคีย์

```
group_by_type(items):                           group_by_status(items):
    groups = {}                                     groups = {"ok": [], "out": [], "broken": []}
    ทุก item:                                        ทุก item:
        groups.setdefault(category, [])                 ถ้า status อยู่ใน groups:
              .append(item)                                 groups[status].append(item)
```

| | `group_by_type` | `group_by_status` |
|---|---|---|
| รู้คีย์ล่วงหน้าไหม | ไม่รู้ — สร้างคีย์ใหม่ทันทีที่เจอหมวดที่ยังไม่มี (`setdefault`) | รู้ — มีแค่ 3 สถานะ สร้างครบตั้งแต่ต้น |
| คีย์ที่คืน | เฉพาะหมวดที่พบจริงในข้อมูล | ครบ 3 คีย์เสมอ แม้กลุ่มนั้นว่าง |
| ค่าที่ไม่รู้จัก | — | ข้ามไป ไม่ทำให้พัง |

`group_by_status` คืนครบ 3 คีย์เสมอ เหตุผลเดียวกับ `count_by_status` ของ Neo
คนที่เอาไปใช้ต่อจะได้ไม่ต้องเขียน `.get()` ดักทุกที่

ต่างจาก `count_by_status` ของ Neo ตรงที่ตัวนั้นเก็บแค่ **จำนวน** ส่วน `group_by_status` เก็บ **รายการทั้งใบ**
ใช้ตอนต้องการรู้ว่า "มีอะไรบ้าง" ไม่ใช่แค่ "กี่ชิ้น"

**ทำไมเดินรอบเดียว ไม่วนหาทีละหมวด** — ถ้าวนหาแต่ "กล้อง" ก่อน แล้ววนใหม่หา "เลนส์"
ต้องอ่านข้อมูลทั้งก้อนซ้ำเท่าจำนวนหมวด ชุดข้อมูลของทีมมี 5 หมวด จึงต้องอ่านซ้ำ 5 รอบ

## 3.5 ความซับซ้อน (Big-O)

n = จำนวนรายการ · m = จำนวนใบที่มี `due_date` · k = จำนวนหมวด

| ฟังก์ชัน | เวลา ดีสุด | เวลา เฉลี่ย | เวลา แย่สุด | หน่วยความจำเพิ่ม |
|---|---|---|---|---|
| `bubble_sort` | O(n) | O(n²) | O(n²) | **O(n)** — ก็อป list ก่อนเรียง |
| `merge_sort` | O(n log n) | O(n log n) | O(n log n) | O(n) + stack O(log n) |
| `sort_by_due_date` | O(n + m log m) | O(n + m log m) | O(n + m log m) | O(m) |
| `sort_by_available` | O(n log n) | O(n log n) | O(n log n) | O(n) |
| `group_by_type` · `group_by_status` | O(n) | O(n) | O(n) | O(n) |
| วนหาทีละหมวด (เทียบ) | O(n × k) | O(n × k) | O(n × k) | O(n) |

### merge sort — O(n log n) ทุกกรณี

- **มีกี่ชั้น** — แบ่งครึ่งทุกครั้งจนเหลือชิ้นเดียว n → n/2 → n/4 → … → 1 ใช้ log₂(n) ครั้ง
- **แต่ละชั้นทำงานเท่าไร** — ในชั้นเดียวกัน `_merge` ทุกตัวรวมกันหยิบของครบ n ชิ้นพอดี ชิ้นละหนึ่งครั้ง = O(n)
- **รวม** — O(n) ต่อชั้น × log₂(n) ชั้น = **O(n log n)**
- **ทำไมไม่มีกรณีดีหรือแย่** — `merge_sort` แบ่งที่ `len(items) // 2` เสมอ ไม่ได้ดูว่าข้อมูลเรียงมาแล้วหรือยัง
  ข้อมูลที่เรียงแล้วก็ยังถูกแบ่งและผสานครบทุกชั้น จำนวนชั้นจึงเท่าเดิมทุกกรณี
- **หน่วยความจำ O(n)** — `_merge` สร้าง list `merged` ใบใหม่ และ `items[:middle]` · `items[middle:]` ก็อปข้อมูลออกมาเป็น list ใหม่
  ณ จังหวะใดก็ตาม list ที่ยังใช้อยู่คือของชั้นที่ซ้อนกันอยู่ตอนนั้น ขนาด n/2 + n/4 + … รวมกันเป็นแค่ไม่กี่เท่าของ n
  จึงเป็น O(n) ส่วน recursion ซ้อนกันลึก log₂(n) ชั้น เป็น stack O(log n)

### bubble sort — O(n²) เฉลี่ยและแย่สุด, O(n) ดีสุด

- **แย่สุด** — รอบที่ 1 เทียบ n−1 คู่ รอบที่ 2 เทียบ n−2 คู่ … รวม (n−1) + (n−2) + … + 1 = n(n−1)/2 = **O(n²)**
- **ดีสุด** — ข้อมูลเรียงมาแล้ว รอบแรกเทียบ n−1 คู่แล้วไม่มีการสลับเลย ตัวหยุดทำงาน จบทันที = **O(n)**
  ถ้าไม่มีตัวหยุดนี้ bubble sort จะวนครบทุกรอบเสมอ เป็น O(n²) แม้ข้อมูลเรียงแล้ว
- **หน่วยความจำ O(n) ไม่ใช่ O(1)** — bubble sort ตามตำราสลับในที่ (in-place) ใช้หน่วยความจำเพิ่ม O(1)
  แต่ตัวในโค้ดนี้เริ่มด้วย `result = list(items)` ก็อปทั้ง list ก่อน เพื่อไม่แก้ของเดิม จึงใช้หน่วยความจำเพิ่ม **O(n)**
  การสลับหลังจากนั้นเกิดในที่บน list ที่ก็อปมา

### sort_by_due_date — O(n + m log m)

กรอง `None` ด้วย list comprehension อ่านครบ n รายการ = O(n) ได้ list ใหม่ m ใบ = หน่วยความจำ O(m)
แล้วเรียก `merge_sort` บน m ใบ = O(m log m) รวมเป็น **O(n + m log m)**
เมื่อ m ใกล้ n ก็คือ O(n log n) — ชุด D มี m = 685 จาก n = 1,000

### การจัดกลุ่ม — O(n)

- **เวลา** — เดิน `for item in items` รอบเดียว แต่ละรายการทำงานคงที่ คือเปิดถังใน `dict` (เฉลี่ย O(1)) แล้ว `append` (O(1) amortized)
  n รายการจึงเป็น **O(n)** ไม่ขึ้นกับจำนวนหมวด
- **หน่วยความจำ O(n)** — ทุกรายการถูกใส่ลงถังใดถังหนึ่ง ไม่มีรายการไหนถูกทิ้ง (ยกเว้นสถานะที่ไม่รู้จักใน `group_by_status`)
  ถังเก็บ **ตัวอ้างอิง** ไปที่ record เดิม ไม่ได้ก็อป record ใหม่ ต่างจากการนับของ Neo ที่ใช้ O(1)
- **วนหาทีละหมวด** — อ่านข้อมูลครบ n รายการ k รอบ = **O(n × k)** ชุดข้อมูลของทีม k = 5 จึงอ่าน 5 เท่าของแบบแบ่งถัง

### อ่านผล

1. **ชุดเล็ก (A–C) bubble sort เร็วกว่าหรือพอๆ กับ merge sort** (0.9× · 0.9× · 0.6×)
   merge sort มีต้นทุนคงที่ทุกชั้น — slice สร้าง list ใหม่ เรียกตัวเองซ้ำ และสร้าง `merged` ใบใหม่
   ที่ 10 รายการงานจริงน้อยกว่าต้นทุนพวกนี้ ส่วน bubble sort ก็อป list ครั้งเดียวแล้ววนสลับในที่
   Big-O บอกพฤติกรรมตอน n โตขึ้น ไม่ได้บอกว่าใครชนะที่ n น้อยๆ ถ้าวัดแค่ชุดเล็กจะสรุปผิด
2. **ชุด D merge sort เร็วกว่า bubble sort 34.6 เท่า** (90.516 เทียบกับ 2.619 ms)
   ข้อมูลโตขึ้น 100 เท่าจากชุด A เวลา bubble sort โตจาก 0.011 เป็น 90.516 ms คือหลายพันเท่า
   ตามทฤษฎี n² ข้อมูลโต 100 เท่า เวลาต้องโตราว 10,000 เท่า
   ส่วน merge sort โตจาก 0.013 เป็น 2.619 ms อยู่ในหลักร้อยเท่า ไม่ถึง 300 เท่าที่ทฤษฎี n log n ให้
   (เวลาของชุดเล็กอยู่ในหลักไมโครวินาที อัตราส่วนจึงหยาบ ใช้ดูแนวโน้มเท่านั้น)
3. **`sorted()` เร็วที่สุดทุกชุด** — ชุด D ใช้ 0.124 ms เทียบกับ merge sort ที่เขียนเอง 2.619 ms
   `sorted()` คือ Timsort ที่เขียนด้วยภาษา C ส่วน merge sort ของเราวนลูปด้วย Python ทุกขั้น
   และเรียก `key()` ใหม่ทุกครั้งที่เทียบ ขณะที่ `sorted()` คำนวณ key ครั้งเดียวต่อรายการ
   แต่ทั้งสองเป็น O(n log n) เหมือนกัน ความต่างคือ **ค่าคงที่ (constant factor) ไม่ใช่ Big-O** — โตในอัตราเดียวกันเมื่อข้อมูลโต
4. **การจัดกลุ่มไม่ทำให้รายการหายหรือเกิน** — ชุด D แบ่งได้ 5 หมวด หมวดละ 200 รวม 1,000
   และแบ่งตามสถานะได้ 616 + 242 + 142 = 1,000 ครบทุกรายการ
   ตัวเลขตามสถานะตรงกับ `count_by_status` ของ Neo ในรอบเดียวกัน (ตาราง 2 ใน notebook) ทั้งสามช่อง
   ทั้งหมดได้จากการเดินข้อมูลรอบเดียว ถ้าวนหาทีละหมวดจะต้องอ่านข้อมูล 5 รอบเพื่อได้ผลเดียวกัน

เวลาที่จับได้แกว่งตามจังหวะของเครื่องทุกครั้งที่รัน แต่ลำดับว่าวิธีไหนเร็วกว่าไม่เปลี่ยน

## 3.9 ข้อจำกัด

- **merge sort ไม่ปรับตัวตามข้อมูล** — ข้อมูลที่เรียงมาแล้วก็ยังถูกแบ่งและผสานครบ O(n log n)
  ต่างจาก Timsort ใน `sorted()` ที่ตรวจเจอช่วงที่เรียงแล้วและข้ามงานส่วนนั้นได้
- **ใช้หน่วยความจำเพิ่ม O(n)** — ทุกชั้นสร้าง list ใหม่จากการ slice และการผสาน ต่างจากการเรียงแบบในที่
- **เรียก `key()` ทุกครั้งที่เทียบ** ไม่ได้คำนวณเก็บไว้ครั้งเดียวแบบ `sorted()` ถ้า key คำนวณแพงจะช้าลงตาม
- **`due_date` ต้องเป็นรูปแบบ `YYYY-MM-DD`** — ถ้าเปลี่ยนเป็นแบบอื่น เช่น `DD/MM/YYYY` การเทียบข้อความจะได้ลำดับผิด
  โดยไม่มี error และ binary search ของ Neo จะผิดตามไปด้วย
- **`sort_by_due_date` คืนแค่ใบที่มี `due_date`** — ผลมี m ใบ ไม่ใช่ n ใบ คนเรียกต้องรู้ว่าของที่ไม่มีคนยืมไม่อยู่ในผล
- **`group_by_status` ข้ามสถานะที่ไม่รู้จักแบบเงียบๆ** — ถ้าข้อมูลมีสถานะผิด ผลรวมของสามกลุ่มจะน้อยกว่าจำนวนทั้งหมดโดยไม่แจ้ง
- **กลุ่มเก็บตัวอ้างอิง ไม่ได้ก็อป** — แก้ record ในกลุ่มคือแก้ record ตัวเดิมด้วย
- **ยังไม่ได้ใช้ในเว็บจริง:** `bubble_sort` (มีไว้เทียบอย่างเดียว) · `sort_by_available` · `group_by_type` · `group_by_status`
  — ใช้ใน notebook เท่านั้น ในเว็บใช้แค่ `sort_by_due_date`
- **ไม่มีตัวเลขเวลาของการจัดกลุ่มและของ `sort_by_due_date`** — notebook วัดเฉพาะการเรียงทั้งชุดตาม `available` (ตาราง M1)
