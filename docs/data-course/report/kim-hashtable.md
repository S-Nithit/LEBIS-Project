## 1.1 กระบวนการที่เลือก

ร้านเช่าอุปกรณ์ถ่ายภาพขนาด 1–3 คน ทำงานซ้ำทุกวันด้วยคำถามชุดเดิม

- ลูกค้าถามว่า *"กล้องรหัส CAM-0012 ว่างมั้ย"* — ต้องหาของจากรหัส
- รับของเข้าร้าน — ต้องเพิ่มของ และห้ามมีรหัสซ้ำ
- ปล่อยเช่าและรับคืน — ต้องแก้จำนวนที่ว่าง
- ของชำรุดจนซ่อมไม่ได้ — ต้องตัดออกจากระบบ

ถ้าเก็บของไว้ใน list ธรรมดา ทุกคำถามต้องไล่ดูทีละชิ้นจนเจอ ของยิ่งมากยิ่งช้า
ส่วนนี้จึงเลือกอัลกอริทึมกลุ่ม **Inserting** และ **Deleting** (รวมถึงการค้นจากรหัส)
โดยเขียนตารางแฮชขึ้นเองทั้งหมด ไม่ได้ครอบ `dict` ของ Python

## 1.2 โครงสร้างข้อมูล

อุปกรณ์ 1 รายการเก็บเป็น record 8 ฟิลด์ ใช้ร่วมกันทั้งทีม

`code` · `name` · `category` · `total` · `available` · `borrower` · `due_date` · `status`

ระบบเก็บของไว้ **สองที่คู่กัน**

```
items = [ {CAM-0001 ...}, {LEN-0002 ...}, {TRI-0003 ...} ]    ตัวข้อมูลจริง มีลำดับ
index = HashTable:  "CAM-0001" -> 0 · "LEN-0002" -> 1 · ...    รหัส -> ตำแหน่งใน list
```

| เก็บแบบ | ค้นจากรหัส | เรียงหรือไล่ตามลำดับ |
|---|---|---|
| list อย่างเดียว | O(n) | ได้ |
| ตารางแฮชอย่างเดียว | O(1) เฉลี่ย | ไม่ได้ — ลำดับเป็นลำดับของถัง |
| **list + ดัชนีแฮช** | **O(1) เฉลี่ย** | **ได้** |

เหตุผลที่ต้องเก็บทั้งสองอย่าง: งานส่วนอื่นของระบบต้องการลำดับ — merge sort ของ Kul
เรียงรายการตามวันครบกำหนด และ binary search ของ Neo หาของที่ครบกำหนดก่อนวันที่กำหนด
ตารางแฮชตอบคำถามแบบช่วงหรือแบบเรียงลำดับไม่ได้เลย จึงทิ้ง list ไม่ได้
ราคาที่จ่ายคือหน่วยความจำเพิ่มหนึ่งตาราง และต้องดูแลให้สองที่ตรงกันเสมอ

## 1.3 ตารางแฮช

### ฟังก์ชันแฮช

ใช้ **polynomial rolling hash**

```
h = 0
ทุกตัวอักษร c ในรหัส:   h = (h × 31 + ord(c)) mod 1,000,000,007
เลขถัง = h mod จำนวนถัง
```

- **ตำแหน่งของตัวอักษรมีผล** — `CAM-01` กับ `CAM-10` ได้ถังต่างกัน
  ถ้าใช้วิธีบวกรหัสตัวอักษรเฉยๆ สองรหัสนี้จะได้ค่าเท่ากัน ซึ่งเป็นรูปแบบรหัสที่ร้านใช้จริง
- **ฐาน 31** เป็นจำนวนเฉพาะ เล็กพอให้คูณเร็ว ใหญ่พอให้ค่ากระจาย
- **มอดด้วยจำนวนเฉพาะใหญ่** กันตัวเลขโตไม่จำกัดจนคำนวณช้า

### การชน (collision) และ chaining

การชนคือรหัสต่างกันแต่คำนวณได้ถังเดียวกัน เลี่ยงไม่ได้ เพราะรหัสมีได้ไม่จำกัดแต่ถังมีจำกัด
ใช้วิธี **chaining** — ถังหนึ่งเก็บได้หลายคู่ต่อกันเป็นโซ่ ตอนค้นไปที่ถังนั้นแล้วไล่ดูในโซ่สั้นๆ

### การขยายตาราง

เมื่อ **load factor** (จำนวนข้อมูล ÷ จำนวนถัง) เกิน **0.7** ขยายถังเป็น 2 เท่า แล้วคำนวณถังใหม่ให้ทุกตัว (rehash)
load factor คือความยาวเฉลี่ยของโซ่ จึงเป็นตัวเลขที่บอกว่าตารางยังเร็วอยู่มั้ย

- ตั้งต่ำเกิน — ตารางโปร่ง กินหน่วยความจำ และขยายบ่อย
- ตั้งสูงเกิน — ประหยัดที่ แต่โซ่ยาว ค้นช้า

การขยายมีต้นทุน O(n) ต่อครั้ง แต่เกิดเฉพาะตอนข้อมูลเพิ่มเป็นเท่าตัว
เฉลี่ยต่อการเพิ่มหนึ่งครั้งจึงยังเป็น O(1) (amortized O(1))

## 1.4 การเพิ่ม ปล่อยเช่า รับคืน และตัดออก

ทุกฟังก์ชันตรวจความถูกต้องก่อนแก้ข้อมูล ถ้าไม่ผ่านจะไม่แตะข้อมูลเลย
เพราะถ้าแก้ list ไปแล้วค่อยพังตอนแก้ดัชนี สองที่จะไม่ตรงกันตลอดไป

| ฟังก์ชัน | กรณีที่ปฏิเสธ |
|---|---|
| `add_item` | รหัสซ้ำ · จำนวนไม่ถูกต้อง |
| `borrow_item` | ไม่มีรหัสนี้ · ของชำรุด · ไม่มีของว่าง · ไม่ใส่ชื่อคนเช่า |
| `return_item` | ไม่มีรหัสนี้ · ของไม่ได้ถูกยืมอยู่ |
| `remove_item` | ไม่มีรหัสนี้ · ยังมีของอยู่กับลูกค้า |

**การลบแบบ swap-and-pop** — ลบตัวกลาง list ตรงๆ เป็น O(n) เพราะต้องเลื่อนทุกตัวที่อยู่ข้างหลัง
และตำแหน่งที่ดัชนีจำไว้ของตัวพวกนั้นผิดหมด จึงยกตัวท้ายสุดมาวางทับตำแหน่งที่ลบ
แก้ดัชนีแค่ตัวที่ถูกย้าย แล้วตัดตัวท้ายทิ้ง ทุกขั้นเป็น O(1)
ราคาที่จ่ายคือลำดับใน list เปลี่ยน ซึ่งรับได้ เพราะงานที่ต้องการลำดับเอาไปเรียงเองอยู่แล้ว

## 1.5 ความซับซ้อน (Big-O)

| การทำงาน | เฉลี่ย | แย่สุด | กรณีแย่สุดเกิดเมื่อ |
|---|---|---|---|
| ค้นจากรหัส | O(1) | O(n) | ทุกรหัสไปกองถังเดียวกัน |
| เพิ่ม | O(1) amortized | O(n) | ตรงกับจังหวะขยายตาราง หรือโซ่ยาว |
| ลบ | O(1) | O(n) | โซ่ยาว |
| ขยายตาราง | O(n) ต่อครั้ง | O(n) | — |

**ทำไม O(1) เป็นค่าเฉลี่ย ไม่ใช่กรณีแย่สุด** — ถ้าทุกรหัสแฮชลงถังเดียวกัน ตารางจะเหลือโซ่เส้นเดียวยาว n
การค้นกลายเป็นการไล่ทีละตัวเหมือน list เกิดได้เมื่อฟังก์ชันแฮชกระจายไม่ดี เมื่อไม่ขยายตาราง
หรือเมื่อมีคนจงใจเลือกรหัสที่ชนกันทั้งหมด notebook หัวข้อ 4 แสดงตารางที่ห้ามขยายไว้เทียบ
โซ่เฉลี่ยยาว 15 ตัว ยาวสุด 17 ตัว (ตารางที่ขยายตามปกติยาวสุดแค่ 3 ตัว)
และยิ่งใส่ข้อมูลเพิ่ม โซ่ยิ่งยาวตาม n ซึ่งคือ O(n) ในทางปฏิบัติ สรุปคือ O(1) ไม่ได้มาฟรี
มาจากฟังก์ชันแฮชที่กระจายดีคู่กับการขยายตาราง ขาดข้อใดข้อหนึ่งก็ไหลลงไปเป็น O(n)

## 1.7 ผลการวัด

วัดสามวิธีบนข้อมูลชุดเดียวกัน — วน list, ตารางแฮชที่เขียนเอง และ `dict` ของ Python (ตัวเทียบ)
แต่ละช่องรัน 3 รอบแล้วเฉลี่ยด้วย `time.perf_counter()` เวลาเตรียมข้อมูลไม่ถูกนับรวม
หน่วยเป็นมิลลิวินาที · "เร็วขึ้น" = เวลาวน list ÷ เวลาตารางแฮชที่เขียนเอง

**ตาราง H1 — ค้นทุกรหัสหนึ่งครั้ง**

| ชุด | วน list | HashTable | dict | เร็วขึ้น |
|---|---:|---:|---:|---:|
| A (10) | 0.004 | 0.015 | 0.001 | 0.3× |
| B (12) | 0.005 | 0.017 | 0.001 | 0.3× |
| C (10) | 0.004 | 0.014 | 0.001 | 0.3× |
| D (1,000) | 21.753 | 1.530 | 0.053 | **14.2×** |

**ตาราง H2 — เพิ่มทีละรายการจนครบชุด (ทุกวิธีเช็กรหัสซ้ำก่อนใส่)**

| ชุด | วน list | HashTable | dict | เร็วขึ้น |
|---|---:|---:|---:|---:|
| A (10) | 0.004 | 0.042 | 0.002 | 0.1× |
| B (12) | 0.005 | 0.066 | 0.002 | 0.1× |
| C (10) | 0.004 | 0.041 | 0.002 | 0.1× |
| D (1,000) | 20.625 | 5.902 | 0.112 | **3.5×** |

**ตาราง H3 — ลบทุกรหัสหนึ่งครั้ง**

| ชุด | วน list | HashTable | dict | เร็วขึ้น |
|---|---:|---:|---:|---:|
| A (10) | 0.006 | 0.019 | 0.002 | 0.3× |
| B (12) | 0.005 | 0.020 | 0.001 | 0.3× |
| C (10) | 0.005 | 0.016 | 0.001 | 0.3× |
| D (1,000) | 15.152 | 1.719 | 0.061 | **8.8×** |

**ตาราง H4 — สถานะตารางแฮชหลังใส่ครบชุด**

| ชุด | จำนวน | ถัง | ชน | ขยาย | โซ่ยาวสุด | load factor |
|---|---:|---:|---:|---:|---:|---:|
| A | 10 | 16 | 2 | 1 | 2 | 0.625 |
| B | 12 | 32 | 5 | 2 | 3 | 0.375 |
| C | 10 | 16 | 2 | 1 | 2 | 0.625 |
| D | 1,000 | 2,048 | 374 | 8 | 3 | 0.488 |

### อ่านผล

1. **ชุดเล็ก (A–C) วน list เร็วกว่า** — ไล่ดู 10 ตัวถูกกว่าการคำนวณแฮชทีละครั้ง
   Big-O บอกพฤติกรรมตอน n โตขึ้น ไม่ได้บอกว่าใครชนะที่ n น้อยๆ ถ้าวัดแค่ชุดเล็กจะสรุปผิด
2. **ชุด D ตารางแฮชชนะทั้งสามงาน** — ข้อมูลโตขึ้น 100 เท่าจากชุด A
   เวลาค้นด้วยการวน list โตขึ้นราว 5,438 เท่า (ค้น n ครั้ง ครั้งละเฉลี่ยครึ่งรายการ = n²/2)
   ส่วนตารางแฮชโตราว 102 เท่า คือโตตาม n เท่านั้น
3. **การเพิ่มชนะน้อยที่สุด (3.5×)** เพราะตารางแฮชเสียเวลาขยายตาราง 8 ครั้งระหว่างใส่ 1,000 รายการ
   ต้นทุนนี้ถูกเฉลี่ยไปทั้งชุด (amortized) จึงยังโตตาม n ไม่ใช่ n²
4. **ชนเยอะแต่โซ่สั้น** — ชุด D ชน 374 ครั้ง แต่โซ่ยาวสุดแค่ 3 เพราะขยายตารางทุกครั้งที่ load factor เกิน 0.7
   นี่คือหลักฐานว่าการชนไม่ใช่ปัญหา ถ้าโซ่ไม่ถูกปล่อยให้ยาว
5. **`dict` ของ Python เร็วกว่าของเรา** ราว 28–29 เท่าตอนค้นและลบ และราว 53 เท่าตอนเพิ่ม
   (`dict` ขยายตัวเองในภาษา C ส่วนของเรา rehash ทีละตัวด้วย Python)
   แต่เป็น O(1) เหมือนกัน ต่างกันที่ค่าคงที่ — โตในอัตราเดียวกัน

เวลาที่จับได้แกว่งตามจังหวะของเครื่องทุกครั้งที่รัน แต่ลำดับว่าวิธีไหนเร็วกว่าไม่เปลี่ยน
